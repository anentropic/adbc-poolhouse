<objective>
Implement the two async prepared-statement methods on `AsyncCursor` as offload wrappers over
the sync ADBC `dbapi.Cursor` methods of the same name, and extend the `_SyncCursor` structural
Protocol with both signatures. Each method is a near-exact clone of `AsyncCursor.execute`
(`_cursor.py:200`) — the ONLY differences are the wrapped callable, the return annotation
(cast off the `-> object` Protocol), and the ABSENCE of `on_abort=self._owner.invalidate`
(D-35-04: cancellable but non-poisoning). Each carries a full Google-style docstring
(Args/Returns/Raises + `Example:`). This turns the plan 35-01 RED tests GREEN.

Purpose: Close the LAST async/sync parity gap (PREP-01/02). The phase is assembly, not
invention — clone `execute` twice, drop `on_abort`, add two Protocol lines. A reviewer should
be able to diff the new methods against `execute` and see only: the callable, the return type,
and the missing `on_abort`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| async task → AsyncCursor | Caller supplies `operation` (SQL) + optional `parameters`, forwarded verbatim to the sync ADBC cursor — the same object the sync path already trusts |
| offload worker → sync ADBC driver | The blocking C call runs off-loop under the pool limiter; the driver owns SQL binding, statement lifecycle, and abort (`_stmt.cancel`) |

## STRIDE Threat Register

Honest minimal model (per the phase security note): these two methods add read-only-ish
offload wrappers over the sync ADBC cursor. No new inputs (SQL/params forwarded exactly like
`execute`), no new I/O sinks, no auth surface, no new dependencies, no new trust boundary
crossed. Neither method executes the query or writes data. D-35-06: native driver errors
surface unchanged with no new error handling.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-01 | Tampering | `operation` / `parameters` forwarded to the driver | accept | Not poolhouse's boundary — SQL passes to the driver exactly as with sync `adbc_prepare` / `execute`; parameterized queries are the user's responsibility. Poolhouse constructs no SQL and adds no sanitization (D-35-06, mirrors `execute`) |
| T-35-02 | Denial of Service | connection left busy/poisoned after a cancelled or unsupported call | mitigate | Each method brackets its offload in `self._owner._offloading()`; `on_abort` is omitted so a cancelled call fires `adbc_cancel` once and returns a CLEAN connection (non-poisoning, D-35-04). Proven by `test_prep_cancel.py` (`invalidate_call_count == 0`, no hang) and `test_prep_unsupported.py` (`checkedout() == 0` after a native error) |
| T-35-SC | Tampering | package installs | accept (N/A) | No package installs this phase — all symbols ship in `adbc_driver_manager` 1.11.0; no new deps/extras. No legitimacy checkpoint required |
</threat_model>
